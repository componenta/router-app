# Componenta Router App

Интеграционный пакет для `componenta/router` в Componenta-приложении. Пакет добавляет обнаружение маршрутов по `#[Route]`, сборку карты через `app:build`, загрузчик HTTP-маршрутизации и резолвер обработчиков маршрута через HTTP-перехватчики.

Если коду нужно только сопоставить путь с маршрутом, сгенерировать URL или выполнить найденный маршрут без HTTP-перехватчиков, он должен зависеть от `componenta/router`. `componenta/router-app` связывает роутер с обнаружением классов и конвейером перехватчиков приложения.

## Зависимости

Версия PHP:

| Требование | Версия |
|---|---|
| PHP | `^8.5.13` |

Пакеты:

| Пакет | Назначение |
|---|---|
| `componenta/app` | Регистрация загрузчиков и участников сборки, публикация и чтение артефактов. |
| `componenta/app-http` | HTTP-точка загрузки, в которую при старте добавляются промежуточные обработчики маршрутизации. |
| `componenta/router` | Записи маршрутов, сопоставление запроса с маршрутом, генерация URL, выполнение маршрута и кеш маршрутов. |
| `componenta/class-finder` | Общий исходный итератор классов, если в приложении настроено обнаружение классов. |
| `componenta/config` | Общий объект конфигурации и ключи, используемые роутером. |
| `componenta/di` | Регистрация фабрик и сервисов, которые контейнер собирает автоматически, через `ConfigProvider`. |
| `componenta/http-responder` | `Responder` для результата обработчика, если обработчик вернул не PSR-7 ответ. |
| `componenta/interceptor` | HTTP-конвейер перехватчиков для `InterceptedRouteHandlerResolver`. |
| `componenta/middleware-factory` | Регистрация резолвера промежуточных обработчиков для обработчиков маршрутов. |
| `componenta/path-resolver` | Разрешение путей к файлу маршрутов относительно корня приложения. |
| `componenta/reflection` | Чтение `#[Route]` с класса и родительских объявлений. |
| `componenta/tokenizer` | Информация о найденном классе при сканировании исходников. |
| `componenta/var-export` | Проверка возможности экспорта подготовленных данных маршрутов; файлами артефактов управляет App. |
| `psr/container` | Получение зависимостей из контейнера. |
| `psr/http-message` | Контракты ответов, которые используют обработчики маршрутов. |
| `psr/http-server-middleware` | Контракты промежуточных обработчиков, которые использует выполнение маршрута. |

Установка:

```bash
composer require componenta/router-app
```

Регистрируйте провайдер после провайдера базового роутера. Это важно, потому что `router-app` заменяет фабрику `RouteLocatorInterface` на интеграционную:

```php
return [
    new Componenta\Http\Router\ConfigProvider(),
    new Componenta\Http\Router\App\ConfigProvider(),
];
```

## Что регистрирует пакет

`Componenta\Http\Router\App\ConfigProvider` добавляет:

| Сервис или ключ | Что регистрируется |
|---|---|
| `RouteLocatorInterface` | `RouteLocatorFactory` из `router-app`, которая выбирает исходный локатор или карту в production. |
| `RouteBuilder` | Фабрика участника сборки с исходным локатором и генератором кеша, использующим настроенный компилятор маршрутов. |
| `AppConfigKey::BUILDERS` | Добавляет `RouteBuilder` к обычной команде `app:build`. |
| `InterceptedRouteHandlerResolver` | Фабрика резолвера обработчиков маршрута через HTTP-перехватчики. |
| `AppConfigKey::BOOTLOADERS` | Добавляет `RoutingBootloader` для HTTP-приложений. |
| `AttributeRouteLocator` | Получает общий исходный итератор через DI и читает его при запросе маршрутов. При отключённом обнаружении классов использует только файл маршрутов. |
| `RouterConfigKey::HANDLER_RESOLVER` | Заменяет алиас единого резолвера обработчиков на `InterceptedRouteHandlerResolver`. |
| `ConsoleConfigKey::COMMANDS` | Добавляет `RouterListCommand` с командой `router:list`. |
| `RouterConfigKey::ROUTES_FILE` | Задает файл маршрутов по умолчанию: `config/routes.php`. |

Базовые записи маршрутов, `Router`, `Routes`, `MatchRouteMiddleware`, `DispatchRouteMiddleware`, `RouteHandlerResolver`, `CompilerInterface`, `MatcherInterface` и `GeneratorInterface` остаются в `componenta/router`.

## HTTP-загрузка

`RoutingBootloader` работает только в HTTP-области приложения. При старте он добавляет `MatchRouteMiddleware` и `DispatchRouteMiddleware` в HTTP-точку загрузки с приоритетом `50`:

```php
$app->pipe(Componenta\Http\Router\Middleware\MatchRouteMiddleware::class, priority: 50);
$app->pipe(Componenta\Http\Router\Middleware\DispatchRouteMiddleware::class, priority: 50);
```

Приложения, которые используют `componenta/app-http` и регистрируют провайдер этого пакета, не должны добавлять эти два промежуточных обработчика вручную. Обработчики, которые должны выполняться раньше маршрутизации, например обработка ошибок или разбор тела запроса, регистрируйте в `config/pipeline.php` с более высоким приоритетом, например `100`.

## Обнаружение маршрутов

`AttributeRouteLocator` реализует `RouteLocatorInterface`, `ClassListenerInterface` и `FinalizableListenerInterface`. В режиме разработки `RouteLocatorFactory` возвращает именно его.

Порядок работы:

1. `AttributeRouteLocatorFactory` берёт `ConfigKey::ROUTES_FILE`, разрешает путь через `PathResolverInterface` и создаёт исходный `RouteLocator` с настроенным компилятором и `useCache: false`.
2. При первом запросе маршрутов `AttributeRouteLocator` обходит общий исходный итератор и передаёт найденные классы в свой `handle()`.
3. Локатор читает `#[Route]` через `Reflection::getDeepMetadata()` и сортирует найденные атрибуты по `priority` от большего к меньшему.
4. Загружаются явные маршруты из файла; затем атрибутные маршруты добавляются в коллекцию как `RouteRecord`.
5. Обычный `getRoutes()` сохраняет полученную коллекцию для текущего запуска. Вызов с явным контекстом заново загружает файл с этими значениями и использует тот же снимок найденных атрибутов.

Локатор больше не регистрируется обязательным слушателем общего обнаружения классов. Если `ConfigDefinition::discovery` не задан, он загружает только файл маршрутов. Такой режим поддерживает сборку, запуск из подготовленной карты и обращения с явным контекстом без регистрации пустого итератора вручную.

Пример контроллера:

```php
use Componenta\Http\Router\Attribute\Route;
use Psr\Http\Message\ResponseInterface;

#[Route(
    name: 'posts.show',
    path: '/posts/[id:\d+]',
    methods: 'GET',
    middlewares: ['web'],
)]
final readonly class ShowPostController
{
    public function __invoke(int $id): ResponseInterface
    {
        // ...
    }
}
```

Атрибут описывает только маршрут. Как выполняются промежуточные обработчики и обработчик, определяют `componenta/router` и `componenta/middleware-factory`.

`methods` можно передать строкой (`'GET'`), строкой с разделителем `|` (`'GET|POST'`) или массивом (`['GET', 'POST']`). Если несколько атрибутных маршрутов могут совпасть с одним URI, раньше будет добавлен маршрут с большим `priority`.

## Файл маршрутов

Даже при обнаружении атрибутов `ConfigKey::ROUTES_FILE` остается точкой входа для маршрутов. Этот пакет задает значение по умолчанию `config/routes.php`. Используйте этот файл для ручной регистрации маршрутов, групп и общих настроек или переопределите ключ конфигурации, если приложение хранит маршруты в другом месте.

```php
use Componenta\Http\Router\Routes;

/** @var Routes $routes */

$api = $routes->group('api', '/api', middleware: ['api']);
$api->get('health', '/health', HealthController::class);
```

Исходный локатор добавляет атрибутные маршруты к маршрутам из этого файла. Билдер получает оба набора через тот же локатор.

## Сборка и запуск

`RouteBuilder` реализует `ApplicationBuilderInterface` и регистрируется в
`app.builders`. Стандартная команда `app:build` вызывает `ApplicationBuildRunner`,
который заново загружает исходную конфигурацию и создаёт отдельный контейнер для
сборки. Ранний обработчик команды должен работать до обычной загрузки приложения.
Создание команды и показ справки не создают участника сборки и не запускают
обнаружение классов. Обычный запуск приложения не выполняет сборку.

Участник сборки получает исходный локатор и `RouteCacheGenerator` с настроенным
компилятором. Метод `build(BuildContext $build)` записывает данные в артефакт
`router.routes` с версией схемы `RouteCacheGenerator::CACHE_VERSION`. App отвечает
за сериализацию, промежуточное хранение, манифест поколения и публикацию всей
сборки. Адаптер роутера не записывает отдельный кеш-файл.

Карта фиксирует исходные определения на момент сборки. После изменения маршрутов,
конфигурации или внешних значений, используемых файлом маршрутов, выполните
`app:build` заново. Исходный и подготовленный режимы сравниваются на одинаковых
входных данных.

В режиме разработки используется `AttributeRouteLocator`. В production при
включённом `COMPILED_PIPELINE` локатор читает `router.routes` из `PreparedBuild`,
который App выбрал при загрузке приложения. Выбранная сборка доступна под
`AppConfigKey::PREPARED_BUILD`; проверка этого строкового идентификатора исключает
автоматическое создание отсутствующего сервиса по имени класса контейнером.
Все читатели используют одно выбранное поколение.

Если необязательный артефакт отсутствует, пропущен при сборке, несовместим или
содержит недопустимые данные, локатор использует исходный файл и общий исходный
итератор классов, когда он настроен. Режим для обычных запросов выбирается один раз
на экземпляр локатора. Если политика запуска требует `router.routes`, локатор
использует подготовленную карту независимо от `APP_ENV` и отклоняет отсутствующую
или недопустимую карту вместо перехода к исходникам. Явное отключение подготовки
противоречит этой политике. В остальных случаях `APP_DISCOVERY_SOURCE=1` отключает
подготовленный путь. Явный контекст `getRoutes($context)` всегда передаётся
источнику, не меняя режим обычных запросов.

Неподдерживаемые компиляторы, синтаксисы, пользовательские атрибуты и значения,
которые нельзя экспортировать с сохранением поведения, приводят к
`$build->skip()` с указанием причины. После успешной публикации такого поколения
его маршруты читаются из исходников; артефакт из предыдущего поколения не
подставляется. Другие ошибки исходников, компиляции и записи прерывают публикацию.

`app:clean` снимает публикацию общей сборки. Уже работающие приложения сохраняют
доступ к выбранному поколению до следующей загрузки.

Пример конфигурации:

```php
use Componenta\Http\Router\ConfigKey;

return [
    ConfigKey::ROUTES_FILE => 'config/routes.php',
    ConfigKey::COMPILED_PIPELINE => true,
];
```

Каталог сборки и идентификатор развёртывания `APP_BUILD_ID` принадлежат App.
`ROUTES_CACHE_FILE` остаётся настройкой самостоятельного роутера; этот адаптер её
не использует. Путь артефакта `router.routes` нельзя перенаправить на исходный файл.

## Миграция

Удалите регистрации `RouteCacheCompiler` и старых участников автоматического
сбора маршрутов. `RouteBuilder` уже регистрируется провайдером пакета; локатор
больше не является обязательным слушателем обнаружения классов. После обновления
выполните `app:build` и удалите прежние отдельные кеш-файлы маршрутов.

Конструктор `RouteBuilder` принимает исходный локатор и генератор кеша, а
`build()` требует `BuildContext`. Отдельные методы `clean()` и
`RouteLocatorFactory::cacheFile()` удалены; очисткой управляет `BuildStore` App.
При ручном создании `PreparedRouteLocator` передаются выбранный `PreparedBuild`
и замыкание исходного локатора.

## HTTP-перехватчики

`InterceptedRouteHandlerResolver` находится в `componenta/router-app`, потому что это интеграция роутера с HTTP-конвейером перехватчиков приложения. Базовый `componenta/router` выполняет обработчик напрямую через `RouteHandlerResolver` и не зависит от `componenta/interceptor`.

Базовый провайдер роутера регистрирует единый идентификатор резолвера
`RouterConfigKey::HANDLER_RESOLVER`. Провайдер `router-app`, подключённый после
базового, заменяет его алиас на `InterceptedRouteHandlerResolver`. Отдельный
конкурирующий резолвер в `MiddlewareConfigKey::RESOLVERS` не добавляется.

Фабрика `InterceptedRouteHandlerResolverFactory` берет:

| Зависимость | Откуда берется |
|---|---|
| `CallableExecutorInterface` | Из контейнера. |
| `PipelineInterface` | Из контейнера. Регистрируется пакетом `componenta/interceptor`. |
| `Responder` | Из контейнера при первом результате, которому требуется преобразование в ответ. |

Обработчики и функции перехвата, возвращающие `ResponseInterface`,
`MiddlewareInterface` или `RequestHandlerInterface`, не требуют создания
`Responder` и настройки его HTTP-фабрик. Преобразование других результатов
использует responder приложения, в том числе экземпляр с отложенной
инициализацией. Ошибки его настройки и создания ответа передаются вызывающему
коду при фактическом обращении. Это поведение одинаково для исходных и
подготовленных маршрутов.

HTTP-конвейер перехватчиков создает `componenta/interceptor`. Его фабрика всегда добавляет `ParameterResolvingInterceptor`, а затем подключает сервисы перехватчиков из списка `Componenta\Interceptor\ConfigKey::HTTP_INTERCEPTORS`. Обычное HTTP-приложение добавляет в этот список `AttributeInterceptor::class`, чтобы обработчики маршрутов могли использовать `#[Intercept]`.

## Границы пакета

Используйте `componenta/router`, когда нужны:

- ручная регистрация маршрутов;
- сопоставление URI и HTTP-метода;
- генерация URL;
- группы маршрутов;
- PSR-15 промежуточные обработчики сопоставления и выполнения маршрута;
- загрузка уже скомпилированного кеша маршрутов.

Используйте `componenta/router-app`, когда нужны:

- обнаружение `#[Route]` в исходниках приложения;
- подготовка карты маршрутов командой `app:build`;
- добавление промежуточных обработчиков роутера в HTTP-приложение при старте;
- выполнение обработчика маршрута через HTTP-перехватчики.

Повторный вызов участника сборки заново загружает файл маршрутов в рамках общего снимка обнаруженных классов и не изменяет ранее созданную коллекцию текущего запуска. Допустимость подготовки определяет генератор кеша роутера: неподдерживаемые настройки компилятора или синтаксиса сохраняют исходный путь. Ошибки определения маршрутов не скрываются и прерывают сборку.
